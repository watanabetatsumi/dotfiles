# Interactive Local Review

ローカルのブランチ差分を分析し、論点をリストアップした上でユーザーと1つずつ対話的に議論する。
合意した修正はその場でコードに反映し、すべての論点が解消されるまでループする。

一方的なレビューではなく、ユーザーとの対話を通じてコードの品質を高めることが目的。
Claude自身の気づきもユーザーの疑問も、同じ土俵で議論する。

## Instructions

### Phase 1: 差分の取得と分析

```bash
# 現在のブランチ名
git branch --show-current

# ベースブランチとの差分（引数でベースブランチを指定できる、デフォルト: main）
BASE_BRANCH="${1:-main}"

# 差分の統計
git diff "$BASE_BRANCH"...HEAD --stat

# 変更ファイル一覧
git diff "$BASE_BRANCH"...HEAD --name-only

# コミット履歴
git log --oneline "$BASE_BRANCH"..HEAD

# 差分の詳細
git diff "$BASE_BRANCH"...HEAD
```

変更が大きい場合は、ファイルごとに Read ツールで現在のコードを確認し、コンテキストを十分に理解する。
未コミットの変更がある場合は `git diff` も確認する。

### Phase 2: 論点の洗い出し

差分を分析し、以下の観点で論点を洗い出す：

**分析観点:**
- **正確性**: ロジックの誤り、エッジケースの見落とし、オフバイワンエラー
- **セキュリティ**: インジェクション、認証/認可の不備、機密情報の露出
- **設計**: 責務の分離、命名の適切さ、抽象化の度合い
- **パフォーマンス**: N+1問題、不要な計算、メモリリーク
- **保守性**: 複雑度、テストの有無、ドキュメントの必要性
- **一貫性**: プロジェクト内の既存パターンとの整合性

**論点の分類:**
- **Critical**: バグ、セキュリティ問題、データ損失リスク — 必ず修正
- **Important**: 設計改善、パフォーマンス問題、テスト不足 — 強く推奨
- **Discussion**: 設計判断、トレードオフ、代替案 — 議論で方向性を決める
- **Minor**: スタイル、命名の改善、軽微なリファクタリング — 任意対応

### Phase 3: 論点リストの提示

AskUserQuestion で論点リストを提示する。

```
提示形式:

## ローカルレビュー 論点一覧

ブランチ `feature/xxx` の変更を分析しました（vs main）。
変更ファイル: X件、追加: +Y行、削除: -Z行

以下の論点を検出しました。1つずつ議論していきます。

### Critical (X件)
1. [ファイル名:行番号] 論点の概要

### Important (X件)
2. [ファイル名:行番号] 論点の概要

### Discussion (X件)
3. [ファイル名:行番号] 論点の概要

### Minor (X件)
4. [ファイル名:行番号] 論点の概要

気になる点があれば追加してください。
```

AskUserQuestion の選択肢：
- **このまま進める**: リストの順に議論開始
- **論点を追加したい**: ユーザーが自分の気になる点を追加
- **特定の論点をスキップ/削除**: 不要な論点を除外

ユーザーが論点を追加した場合は、リストに組み込んで再提示する。

### Phase 4: 各論点の対話的議論と修正

Critical → Important → Discussion → Minor の優先度順に、1つずつ議論する。

各論点について AskUserQuestion で以下のように提示：

```
## 論点 X/Y: [カテゴリ] ファイル名:行番号

**現在のコード:**
```[lang]
[該当箇所のコードを引用]
```

**指摘内容:**
[具体的に何が問題/議論対象かを説明]

**修正案:**
```[lang]
[具体的な修正コード]
```

**質問:**
[ユーザーの判断を仰ぐ質問]
```

AskUserQuestion の選択肢は論点に応じて柔軟に設定するが、基本パターン：
- **修正案を適用する (Recommended)**: Edit ツールで修正を適用
- **背景を説明したい**: ユーザーが意図を説明し、再議論
- **別の修正案にしたい**: ユーザーの案を聞いて反映
- **対応不要、スキップ**: この論点をスキップ

**修正の適用:**
- ユーザーが同意した修正は、即座に Edit ツールでコードに反映する
- 修正後、変更内容を簡潔に報告してから次の論点へ進む

**対話のルール:**
- ユーザーが背景を説明した場合、それを踏まえて論点を再評価する
- 説明に納得した場合は「なるほど、それなら問題ありません」と論点を取り下げる
- まだ懸念がある場合は、具体的に何が気になるかを改めて説明する
- 対話は納得するまで続ける。一度で合意する必要はない
- ユーザーが別の修正案を提案した場合は、その案の妥当性を議論した上で適用する

### Phase 5: ユーザーの追加論点

全論点の議論が終わったら、AskUserQuestion で確認：

```
質問: すべての論点を議論しました。他に気になる点はありますか？
```

- **他に気になる点がある**: ユーザーの指摘を受けて追加議論（Phase 4 に戻る）
- **レビュー完了**: Phase 6 へ
- **変更サマリーを確認したい**: 適用した修正の一覧を表示

ユーザーが追加の論点を出した場合は、Phase 4 と同様に議論し修正する。

### Phase 6: 再分析ループ

修正を適用した場合、変更後のコードに新たな問題が生じていないかを再分析する。

```bash
# 修正後の差分を確認
git diff
```

再分析で新たな論点が見つかった場合：
- AskUserQuestion で新たな論点を提示
- Phase 4 と同様に議論

新たな論点がなければ Phase 7 へ。

### Phase 7: 完了サマリー

レビューの結果をサマリーとして表示：

```markdown
## ローカルレビュー完了

### ブランチ情報
- **ブランチ**: feature/xxx
- **ベース**: main
- **変更ファイル数**: X件

### レビュー結果

#### 修正を適用 (X件)
| ファイル | 内容 | カテゴリ |
|---------|------|---------|
| src/api/handler.ts:42 | null チェックを追加 | Critical |
| src/utils/validate.ts:15 | 変数名を改善 | Minor |

#### 議論の結果スキップ (X件)
| ファイル | 内容 | 理由 |
|---------|------|------|
| src/config.ts:8 | 定数の外出し | 現時点では不要と判断 |

#### 最初からスキップ (X件)
| ファイル | 内容 |
|---------|------|
| ... | ... |

### 未コミットの変更
[git diff --stat の結果]
```

AskUserQuestion で次のアクションを確認：
- **変更をコミットする**: smart-commit スキルに引き継ぐ
- **さらに修正を続ける**: 追加の変更を行う
- **これで終了**: セッション終了

## 重要な原則

### レビューの心構え
- **対話を通じて理解を深める**: なぜそう書いたのかを聞き、文脈を理解してから判断する
- **自分の懸念も率直に伝える**: 気になる点があれば遠慮せず提示する。ただし押し付けない
- **背景を尊重する**: ユーザーの説明に納得したら素直に取り下げる
- **修正は合意の上で**: 勝手にコードを変更しない。必ず議論と合意を経てから Edit する

### 対話のループ
このスキルの核心は「解消するまでループ」すること。
- 各論点は合意に達するまで対話を続ける
- 全論点の議論後、ユーザーの追加指摘を受け付ける
- 修正適用後に再分析し、新たな問題がないか確認する
- ユーザーが「完了」と言うまでレビューセッションは続く
